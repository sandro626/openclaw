# gstack-architecture 工程评审

工程经理视角的方案评审。在动手写代码之前，把方案锁死。

**承载 agent**: cto, dev
**触发场景**: "架构评审"、"技术方案评审"、"eng review"、"review the architecture"

## 使用时机

- 有设计文档或方案描述，准备开始编码前
- 对现有系统做大改动前
- 评审第三方提交的技术方案

## 评审维度

### 1. 架构 (Architecture)

组件边界、职责划分、依赖关系、可扩展性。

| 分数 | 标准                                             |
| ---- | ------------------------------------------------ |
| 9-10 | 职责清晰、耦合低、易扩展，有图表说明数据流和依赖 |
| 7-8  | 大体合理，个别边界模糊但不影响实现               |
| 5-6  | 存在循环依赖或职责混乱，需要调整后才能动手       |
| 0-4  | 架构不清，无法判断是否能跑通                     |

**关键问题**:

- 哪些组件负责哪些职责？边界在哪？
- 依赖方向是否单向？有没有循环依赖？
- 新增组件是否必要？能否复用现有组件？
- 如果用户量翻 10 倍，哪里先扛不住？

### 2. 数据流 (Data Flow)

数据从输入到输出的完整路径，包括转换、存储、传递。

| 分数 | 标准                                                         |
| ---- | ------------------------------------------------------------ |
| 9-10 | 每条数据流有明确的输入源、转换逻辑、输出目标，异常路径有说明 |
| 7-8  | 主路径清晰，个别分支路径描述不足                             |
| 5-6  | 数据流有断裂或歧义，实现时需要猜测                           |
| 0-4  | 无法追踪数据从哪来到哪去                                     |

**关键问题**:

- 数据从哪来？（API / 数据库 / 消息队列 / 用户输入）
- 经过了哪些转换？格式变化是什么？
- 存在哪里？读写频率？
- 数据一致性如何保证？

### 3. 边界条件 (Edge Cases)

空值、超长输入、并发冲突、网络超时、部分失败。

| 分数 | 标准                                    |
| ---- | --------------------------------------- |
| 9-10 | 列出至少 5 个关键边界条件并给出处理策略 |
| 7-8  | 覆盖常见边界条件，极端场景未考虑        |
| 5-6  | 只考虑了 happy path，边界条件明显遗漏   |
| 0-4  | 方案中未提及边界条件                    |

**关键问题**:

- 输入为空 / null / 空数组时怎么办？
- 并发写入同一资源怎么办？
- 下游服务超时或返回异常数据怎么办？
- 部分失败时是全部回滚还是部分保留？

### 4. 错误处理 (Error Handling)

错误传播、降级策略、重试机制、用户可见的错误信息。

| 分数 | 标准                                                           |
| ---- | -------------------------------------------------------------- |
| 9-10 | 每类错误有明确的处理策略（重试/降级/熔断），用户能看到有用信息 |
| 7-8  | 核心路径有错误处理，非核心路径可能静默失败                     |
| 5-6  | 错误被吞掉或只打 log，无恢复策略                               |
| 0-4  | 无错误处理                                                     |

**关键问题**:

- 哪些错误可以重试？重试几次？间隔？
- 哪些错误需要降级？降级到什么？
- 用户看到的错误信息是否有用（不是 "系统错误"）？
- 错误是否会级联传播导致雪崩？

### 5. 测试覆盖 (Test Coverage)

单元测试、集成测试、E2E 测试的覆盖计划。

| 分数 | 标准                                                  |
| ---- | ----------------------------------------------------- |
| 9-10 | 列出每个功能点的测试类型和关键断言，覆盖率目标 >= 80% |
| 7-8  | 核心功能有测试计划，边界条件测试不足                  |
| 5-6  | 只提到 "需要写测试" 但无具体计划                      |
| 0-4  | 未提及测试                                            |

**关键问题**:

- 哪些路径必须有单元测试？
- 哪些跨组件交互需要集成测试？
- 是否有回归风险？有回归测试吗？
- 测试数据从哪来？如何 mock 外部依赖？

### 6. 性能 (Performance)

响应时间、吞吐量、内存占用、数据库查询效率。

| 分数 | 标准                                       |
| ---- | ------------------------------------------ |
| 9-10 | 有性能基线和目标，识别了瓶颈并给出优化方案 |
| 7-8  | 考虑了主要性能点，个别热点未分析           |
| 5-6  | 提到了性能但无具体指标或方案               |
| 0-4  | 未考虑性能                                 |

**关键问题**:

- 预期的 QPS / 响应时间是多少？
- 有没有 N+1 查询？全表扫描？
- 有缓存策略吗？缓存失效怎么办？
- 大数据量场景（分页 / 批量处理）怎么处理？

### 7. 安全 (Security)

认证、授权、数据校验、敏感信息保护。

| 分数 | 标准                                                     |
| ---- | -------------------------------------------------------- |
| 9-10 | 识别了所有攻击面，有输入校验、权限控制、敏感数据脱敏方案 |
| 7-8  | 核心安全措施到位，非核心路径可能疏漏                     |
| 5-6  | 只有基础认证，缺乏细粒度授权和输入校验                   |
| 0-4  | 未考虑安全                                               |

**关键问题**:

- 谁能访问？权限粒度是什么？
- 用户输入是否校验和转义？
- 敏感数据（密码、token、个人信息）如何存储和传输？
- 有没有 SQL 注入 / XSS / CSRF 风险？

## 必答问题清单

以下问题必须在评审中答清楚才能动手。如果方案没有覆盖，标记为 **阻塞项**：

1. **要改什么？** 改动范围涉及哪些文件 / 模块 / 服务？
2. **改完什么样？** 改完后的预期行为是什么？有示例吗？
3. **什么会坏？** 改动可能影响哪些现有功能？回归风险多大？
4. **最坏情况？** 上线后出问题，影响范围多大？能快速回滚吗？
5. **怎么验证？** 上线后怎么确认功能正确？有监控指标吗？

## 输出格式

评审完成后，输出以下结构：

```
## 评审结果

### 维度评分

| 维度 | 评分 | 说明 |
|------|------|------|
| 架构 | X/10 | 一句话评价 |
| 数据流 | X/10 | 一句话评价 |
| 边界条件 | X/10 | 一句话评价 |
| 错误处理 | X/10 | 一句话评价 |
| 测试覆盖 | X/10 | 一句话评价 |
| 性能 | X/10 | 一句话评价 |
| 安全 | X/10 | 一句话评价 |
| **综合** | **X/10** | |

### 风险列表

| # | 风险 | 严重程度 | 影响 | 建议 |
|---|------|----------|------|------|
| 1 | 具体风险描述 | 高/中/低 | 影响范围 | 处理建议 |

### 阻塞项

- [ ] 未回答的必答问题

### 建议

1. 动手前必须解决的问题
2. 建议优先补充的内容
3. 可以后续优化的部分
```

### 综合评分规则

7 个维度取加权平均：

- 架构 x 1.5
- 数据流 x 1.0
- 边界条件 x 1.0
- 错误处理 x 1.0
- 测试覆盖 x 1.5
- 性能 x 1.0
- 安全 x 1.0

权重总和 8.0，综合分 = 加权总分 / 8.0，四舍五入取整。

### 评审结论

| 综合分 | 结论       | 动作                 |
| ------ | ---------- | -------------------- |
| >= 8   | 通过       | 可以动手，关注建议项 |
| 6-7    | 有条件通过 | 解决阻塞项后动手     |
| < 6    | 不通过     | 需要重做方案         |
