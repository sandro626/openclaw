# gstack-investigate：系统化根因排查

为 OpenClaw 机器人提供结构化的根因排查能力。四阶段流程，强制要求找到根因后才能修复。

**承载 agent:** dev, cto, pc-backend, pc-frontend

**触发场景:** "排查问题"、"为什么报错"、"根因分析"、"debug"、"investigate"、"troubleshoot"、"为什么不通"

---

## 铁律

**没有找到根因，就不能修。**

修症状 = 打地鼠。每次修症状而不修根因，下一个 bug 会更难找。

违反铁律的信号：

- "先快速修一下" — 不存在"先修一下"
- 还没追踪数据流就提修复方案 — 在猜
- 每修一个地方，别处冒出新问题 — 修错了层

---

## 第一阶段：调查（Investigate）

收集上下文，不急于下结论。

### 1. 收集症状

- 读错误信息、堆栈跟踪、复现步骤
- 信息不够时，每次只问一个问题，不要一次性问一堆

### 2. 读代码

- 从症状入口沿调用链回溯
- 用 Grep 找所有相关引用，用 Read 理解逻辑

### 3. 查近期变更

```bash
git log --oneline -20 -- <affected-files>
```

之前能用现在不行？根因在 diff 里。

### 4. 尝试复现

- 能确定性地触发吗？不能就继续收集证据，不要猜。

### 调查手段清单

| 手段        | 怎么做                                  | 什么时候用     |
| ----------- | --------------------------------------- | -------------- | ------------- |
| 读日志      | `tail -n 200 /tmp/openclaw-gateway.log` | Gateway 报错   |
| 查代码      | Grep 定位 + Read 理解                   | 所有场景       |
| 查 git 变更 | `git log --oneline -20 -- <files>`      | 回归问题       |
| 复现        | 按描述重放操作                          | 确认问题存在   |
| 对比环境    | 比较本地 vs 服务器配置差异              | 环境相关 bug   |
| 查进程状态  | `ps aux                                 | grep openclaw` | 进程/端口问题 |
| 查端口      | `ss -tlnp                               | grep 18789`    | 连接问题      |
| 查配置      | 读 `openclaw.json` 或 agent 配置        | 配置问题       |

**阶段输出:** 一句具体的、可验证的根因假设。

---

## 第二阶段：分析（Analyze）

检查问题是否匹配已知模式。

### 常见模式

| 模式     | 特征                     | 排查方向                |
| -------- | ------------------------ | ----------------------- |
| 竞态条件 | 间歇性、跟时机有关       | 共享状态的并发访问      |
| 空值传播 | TypeError、Cannot read   | 可选值缺少守卫          |
| 状态损坏 | 数据不一致、部分更新     | 事务、回调、钩子        |
| 集成故障 | 超时、非预期响应         | 外部 API 调用、服务边界 |
| 配置漂移 | 本地能跑、服务器不行     | 环境变量、配置文件      |
| 缓存过期 | 显示旧数据、清缓存后恢复 | Redis/内存缓存          |

### 额外检查

- 同区域是否有过往修复？**同一文件反复出 bug 是架构问题，不是巧合。**
- 搜索已知问题：`git log --all --grep="关键词"`

---

## 第三阶段：假设验证（Hypothesize）

写修复代码之前，先验证假设。

### 验证方法

| 方法       | 做法                       | 适用场景     |
| ---------- | -------------------------- | ------------ |
| 控制变量   | 只改一个条件，观察结果变化 | 多因素问题   |
| 最小复现   | 构造最小触发条件           | 复杂交互问题 |
| 时间线分析 | 按时间排列事件，找异常点   | 间歇性问题   |
| 临时日志   | 在可疑点加 log，确认数据流 | 数据流不明   |
| 断点验证   | 加 assertion 确认假设      | 逻辑分支问题 |

### 假设错了怎么办

1. 回到第一阶段，收集更多证据，不要猜
2. 搜索通用错误模式（脱敏后搜索）
3. **三振规则：3 个假设都不对，停下来。**

停下来时，给用户选项：

- 继续排查 — 我有新假设
- 升级处理 — 需要更熟悉系统的人
- 加日志等下次复现 — 先埋点观测

### 危险信号

- 还没追踪数据流就提修复 — 在猜
- 修了 A 坏了 B — 修错层了
- "应该能修" — 没有验证就不要说"应该"

---

## 第四阶段：修复（Implement）

根因确认后才能进入此阶段。

### 修复原则

1. **修根因，不修症状。** 最小改动消除真正的问题。
2. **最小 diff。** 最少的文件、最少的行数。不要顺手重构周边代码。
3. **写回归测试。** 测试必须：
   - 没有修复时**失败**（证明测试有意义）
   - 有修复时**通过**（证明修复有效）
4. **跑测试。** 贴输出。不允许回归。
5. **影响 >5 个文件时，先确认范围再动手。**

---

## 输出格式

每个排查完成后，输出结构化报告：

```
排查报告
════════════════════════════════════════
现象：      [用户观察到的表现]
根因：      [真正的问题所在]
修复：      [改了什么，附文件:行号]
验证：      [测试输出、复现结果]
回归测试：  [新测试的文件:行号]
状态：      DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```

### 状态说明

- **DONE** — 根因找到，修复完成，回归测试通过
- **DONE_WITH_CONCERNS** — 修复完成但无法完全验证（如间歇性 bug）
- **BLOCKED** — 根因不明确，需要更多信息或人工介入

---

## 重要规则

- 3 次修复失败 → 停下来，质疑架构，不是质疑假设
- 无法验证的修复不要上线
- 不要说"这应该能修"，验证了再说
- 修复影响 >5 个文件 → 先确认影响范围
- 排查过程中只修根因相关代码，不做顺手重构
