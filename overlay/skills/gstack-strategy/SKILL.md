# gstack-strategy — 产品策略三板斧

给 OpenClaw agent 提供从「模糊想法」到「CEO 级取舍评审」的全链路策略能力。
整合 gstack 的三个核心 skill，适配 OpenClaw 机器人场景（企业微信、飞书等 IM 渠道内的产品讨论）。

承载 agent: pc-ceo_assistant, pc-pm

## 触发场景

- "帮我理清思路"
- "产品问题"
- "方案评审"
- "CEO 视角"
- "这个需求值不值得做"
- "帮我想想这个方向对不对"
- "评审一下这个方案"

## 能力一：office-hours（六问重构）

来源：gstack `/office-hours` skill。

用六个强制提问帮用户从模糊想法中找到真正的问题。每次只问一个，追问到具体为止。

### 六个问题

| #   | 问题                                    | 追问目标                             | 红旗信号                           |
| --- | --------------------------------------- | ------------------------------------ | ---------------------------------- |
| 1   | **需求现实** — 谁真的在用？             | 说出具体行为证据（付费、依赖、投诉） | "大家觉得有意思"、"有 500 人注册"  |
| 2   | **现状替代** — 用户现在怎么解决的？     | 具体的替代方案和它的成本             | "现在没有解决方案"（说明痛点不够） |
| 3   | **绝望具体性** — 最痛的那个场景是什么？ | 具体的人名、职位、失败后果           | "中小企业"、"市场团队"（太笼统）   |
| 4   | **最窄楔子** — 最小可行切入？           | 一周内能交付、有人愿意付费的最小版本 | "必须先做完整平台"                 |
| 5   | **可达性** — 怎么触达第一批用户？       | 具体渠道和转化路径                   | "做完再推广"                       |
| 6   | **为什么是现在** — 什么变了？           | 让此刻成为窗口期的具体变化           | "市场在增长 20%"（谁都在说）       |

### 执行要点

- 每次只问一个问题，等用户回答再追问
- 第一个回答通常是修饰过的，追问第二、第三次才到真相
- 不做鼓励，只做诊断：说"这个方向因为 X 证据可行/不可行"，不说"挺好的"
- 如果用户想跳过：选最关键的 2-3 个问题，不全部跳过

### 按产品阶段路由

- 有付费客户 → 重点问 Q4、Q5、Q6
- 有用户未付费 → 重点问 Q2、Q4、Q5
- 还没产品 → 重点问 Q1、Q2、Q3

## 能力二：autoplan（方案自动成型）

来源：gstack `/autoplan` skill。

把模糊需求变成结构化方案。不需要用户逐个回答问题，agent 自主决策。

### 输出格式

```
## 方案：{标题}

### 背景
- 为什么做这个
- 当前系统/流程现状

### 目标
- 具体要达成的结果（可衡量）

### 范围
- 包含什么
- 不包含什么（明确写出）

### 里程碑
1. {阶段1} — 产出 + 预计时间
2. {阶段2} — 产出 + 预计时间
3. ...

### 风险
| 风险 | 可能性 | 影响 | 应对 |
|------|--------|------|------|
| {具体风险} | 高/中/低 | 高/中/低 | {具体方案} |

### 开放问题
- [ ] {待确认的问题}
```

### 执行要点

- 至少给出 2 个方案选项：最小可行版 vs 理想架构版
- 每个方案要说明：复用了什么已有能力、新增什么、风险在哪
- 自动决策原则：选更完整的方案（AI 时代完整比省事便宜）、避免重复造轮子、显式优于花哨
- 如果用户提供了足够清晰的输入，直接出方案不等追问

## 能力三：plan-ceo-review（CEO 取舍评审）

来源：gstack `/plan-ceo-review` skill。

从 CEO 视角做取舍判断：这个方向该继续、转向还是砍掉。

### 四种评审模式

| 模式     | 适用场景           | 核心问题                           |
| -------- | ------------------ | ---------------------------------- |
| 范围扩大 | 新功能、新方向     | "怎么做到 10x 更好？"              |
| 精选扩大 | 功能迭代           | "当前范围是基线，还有什么值得加？" |
| 保持范围 | bug 修复、重构     | "怎么做到滴水不漏？"               |
| 缩减范围 | 方向存疑、资源紧张 | "最小可行版本是什么？"             |

### 核心评审维度

1. **前提假设挑战** — 方案依赖的假设成立吗？有没有反面证据？
2. **10x 产品思维** — 如果投入翻倍，产出能 10x 吗？怎么做到？
3. **范围判断** — 当前范围是太大还是太小？缺什么关键环节？
4. **已有能力复用** — 哪些子问题已经有现成解决方案？
5. **6 个月后悔检查** — 半年后回看，什么决定会显得愚蠢？
6. **竞争风险** — 别人能更快做到吗？壁垒在哪？

### 输出格式

```
## CEO 评审结论

### 方向判断
{继续 / 转向 / 砍掉}

### 核心理由（最多 3 条）
1. {理由}
2. {理由}
3. {理由}

### 前提假设
- [成立] {假设} — 因为 {证据}
- [存疑] {假设} — 因为 {反面证据}

### 范围调整建议
- 保留：{当前范围中正确的部分}
- 增加：{建议加入的部分 + 理由}
- 砍掉：{建议去掉的部分 + 理由}

### 关键风险
- {最大的 1-2 个风险和应对}
```

### 执行要点

- 先确认评审模式再开始
- 假设挑战是最重要的步骤，不能跳过
- 范围调整要给出具体理由，不能只说"可以加一点"
- 最终必须给出明确的继续/转向/砍掉建议，不能两边讨好

## 使用流程

### 流程一：从零开始理思路

```
office-hours（六问）→ autoplan（出方案）→ plan-ceo-review（CEO 评审）
```

适合：用户说"帮我理清思路"、"有个想法但不确定值不值得做"。

### 流程二：已有方案要评审

```
plan-ceo-review（CEO 评审）
```

适合：用户说"帮我评审这个方案"、"这个方向对不对"。

### 流程三：模糊需求要出方案

```
autoplan（出方案）→ plan-ceo-review（CEO 评审）
```

适合：用户说"帮我规划一下"、"出一个方案"。

## 注意事项

- 这个 skill 只产出策略文档和评审结论，不写代码
- 在 IM 渠道（企微、飞书）中使用时，输出要精简，避免超长消息
- 如果讨论涉及公司内部敏感信息，提醒用户注意信息安全
- 评审结论要说人话，不用术语堆砌
