# gstack-qa: 系统化 QA 测试与视觉审计

整合 gstack 的 qa、qa-only、design-review 能力，给 OpenClaw 机器人做浏览器测试和视觉审计。

**承载 agent:** pc-pctester, dev, pc-frontend

**触发场景:** "测试一下"、"QA"、"视觉检查"、"帮我测"、"测试这个页面"、"找 bug"、"回归测试"

## 重要说明

本 skill 只提供测试流程和方法论。浏览器运行时使用 OpenClaw 自带的 `browser` 插件（`extensions/browser`），不引入第二套浏览器 daemon。所有浏览器操作通过 agent 的 browser 工具调用完成。

---

## 两种模式

### 1. Full 模式（测试+修复循环）

适用场景：开发阶段自测、上线前验证、PR 质量把关。

流程：测试 -> 记录问题 -> 修复代码 -> 回归验证 -> 出报告。

参数：

| 参数     | 默认值                               | 示例                                                               |
| -------- | ------------------------------------ | ------------------------------------------------------------------ |
| 目标 URL | 自动检测或必填                       | `https://myapp.com`, `http://localhost:3000`                       |
| 严重级别 | Standard（critical + high + medium） | `--quick`（仅 critical + high）, `--exhaustive`（含 low/cosmetic） |
| 范围     | 全站                                 | `只测支付页面`                                                     |
| 认证     | 无                                   | `用 user@example.com 登录`                                         |

### 2. Report-Only 模式（只出报告）

适用场景：测试报告交付、第三方质量评估、不希望改动代码时。

流程：测试 -> 记录问题 -> 出报告。不修改任何源码。

触发关键词："只看报告"、"report only"、"不要改代码"、"帮我看看就行"

## 测试流程（5 步）

### Step 1: 导航

```
1. 确定目标 URL
2. 使用 browser 插件打开页面
3. 全页截图作为初始状态基线
4. 记录页面框架类型（Next.js / SPA / Rails / WordPress 等）
```

如果需要登录：

- 使用 browser 插件导航到登录页
- 填写表单、提交
- 验证登录状态
- 密码在报告中始终用 `[REDACTED]` 替代

### Step 2: 截图

每个页面至少截 3 张：

| 截图类型             | 用途         | 命名规范               |
| -------------------- | ------------ | ---------------------- |
| 桌面端全页           | 主证据       | `{page}-desktop.png`   |
| 移动端视口 (375x812) | 响应式检查   | `{page}-mobile.png`    |
| 注释截图             | 标注问题区域 | `{page}-annotated.png` |

交互问题额外截图：

- 操作前：`issue-{N}-before.png`
- 操作后：`issue-{N}-after.png`
- 修复前/后对比：`issue-{N}-fix-before.png` / `issue-{N}-fix-after.png`

### Step 3: 交互

在每个页面上执行以下操作：

1. **点击所有可见按钮和链接** -- 检查是否跳转到预期目标
2. **填写表单** -- 测试空值、非法输入、边界值、超长文本
3. **导航路径** -- 检查所有入口和出口
4. **状态切换** -- 空状态、加载中、错误状态、溢出内容
5. **控制台错误** -- 每次交互后检查 JS 错误

### Step 4: 验证

对每个发现的问题：

1. 重现一次 -- 确认不是偶发
2. 记录重现步骤 -- 精确到点击了什么、输入了什么
3. 截图留证 -- 每个问题至少一张截图
4. 评估严重级别 -- critical / high / medium / low

### Step 5: 报告

输出结构化报告，包含：

- 健康评分（0-100）
- 问题列表（含截图引用和重现步骤）
- 修复建议（Full 模式含修复状态）
- Top 3 优先修复项

## 视觉审计要点

### 间距

- 间距是否遵循统一的基准（4px 或 8px 倍数）
- 相关元素是否靠近，不相关元素是否有间距分隔
- 内边距和外边距是否一致
- 模块间距是否有节奏感

### 层级

- 视觉重心是否正确（用户第一眼看到最重要的内容）
- 标题层级是否清晰（h1 > h2 > h3，无跳级）
- 一个视图是否只有一个主 CTA
- 信息密度是否合适

### 一致性

- 导航栏在所有页面是否一致
- 按钮样式是否统一（同级别按钮外观相同）
- 图标风格是否统一（线性/面性/双色不同时混用）
- 文案风格是否统一（正式/口语不随意切换）
- 间距系统是否全站统一

### AI Slop 模式（10 个需警惕的反模式）

这些模式会让页面看起来像 AI 生成的模板：

1. **紫/蓝-紫渐变背景** -- AI 最爱的配色
2. **三列特性网格** -- 圆形图标 + 粗标题 + 两行描述，重复三遍，最典型的 AI 布局
3. **彩色圆形图标** -- SaaS 模板标配
4. **全部居中** -- 所有标题、描述、卡片全部 text-align: center
5. **统一大圆角** -- 所有元素用相同的大 border-radius
6. **装饰性浮球/波浪分割线** -- 空白区域应该放更好的内容，而不是装饰
7. **Emoji 当设计元素** -- 标题里放火箭、用 Emoji 当列表符号
8. **卡片左边框** -- `border-left: 3px solid <accent>` 的套路
9. **泛泛的文案** -- "欢迎使用 X"、"解锁 Y 的力量"、"一站式 Z 解决方案"
10. **流水线节奏** -- hero -> 三列特性 -> 客户评价 -> 定价 -> CTA，每节等高

### 截图命名

```
{page}-{viewport}.png              # 页面截图
{page}-annotated.png               # 标注截图
issue-{N}-{description}.png        # 问题截图
issue-{N}-before.png               # 操作前
issue-{N}-after.png                # 操作后
issue-{N}-fix-before.png           # 修复前
issue-{N}-fix-after.png            # 修复后
```

### 前后对比

Full 模式下修复问题后，必须提供修复前后对比：

1. 修复前截图（已在测试阶段采集）
2. 修复代码（最小改动）
3. 修复后截图（回归验证时采集）
4. 确认无新问题引入

### 控制台错误

每次交互后检查控制台，聚合所有页面的错误：

```
控制台健康度：
- 0 错误 -> 100 分
- 1-3 错误 -> 70 分
- 4-10 错误 -> 40 分
- 10+ 错误 -> 10 分
```

## 健康评分

总分 0-100，按以下权重计算：

| 类别       | 权重 |
| ---------- | ---- |
| 控制台健康 | 15%  |
| 链接完整性 | 10%  |
| 视觉质量   | 10%  |
| 功能正确性 | 20%  |
| 用户体验   | 15%  |
| 性能       | 10%  |
| 内容质量   | 5%   |
| 可访问性   | 15%  |

每个类别起始 100 分，按问题严重度扣分：

| 严重度   | 扣分 |
| -------- | ---- |
| Critical | -25  |
| High     | -15  |
| Medium   | -8   |
| Low      | -3   |

## Full 模式修复循环

### 修复规则

1. **每个问题一个提交** -- 不合并多个修复
2. **最小改动** -- 只修相关问题，不顺带重构
3. **修复后必须回归验证** -- 导航回原页面截图确认
4. **引入新问题立即回滚** -- `git revert HEAD`
5. **自我约束** -- 每修 5 个问题评估风险，风险过高则停下报告

### 修复提交格式

```
fix(qa): ISSUE-NNN -- 简短描述
```

### 严重度筛选

| 模式             | 修复范围                 |
| ---------------- | ------------------------ |
| --quick          | 仅 critical + high       |
| Standard（默认） | critical + high + medium |
| --exhaustive     | 全部，含 low/cosmetic    |

### 修复后验证

每个修复必须：

1. 导航回受影响页面
2. 截取修复后截图
3. 检查控制台无新错误
4. 确认修复有效且无副作用
5. 分类：verified / best-effort / reverted

### 自我约束机制

每修 5 个问题（或任何回滚后），评估风险：

```
风险值起始: 0%
每次回滚: +15%
每次涉及 >3 个文件: +5%
第 15 个修复之后: 每个 +1%
涉及无关文件: +20%
```

风险 > 20% 时暂停，向用户报告进展。硬上限 50 个修复。

## 框架特定检查

### Next.js

- 水合错误（`Hydration failed`）
- `_next/data` 请求 404
- 客户端导航是否正常（点击链接而非直接 URL）
- 动态内容页面的 CLS

### SPA（React / Vue / Angular）

- `links` 命令可能漏掉客户端路由，优先使用 `snapshot -i` 找导航元素
- 导航离开再返回，数据是否刷新
- 浏览器前进/后退是否正常
- 长时间使用后的内存泄漏

### Rails

- N+1 查询警告
- CSRF token 存在性
- Turbo/Stimulus 页面切换是否流畅

## Diff-Aware 模式

当用户在功能分支上说"测试一下"且未提供 URL 时，自动进入 diff-aware 模式：

1. 分析分支变更：`git diff main...HEAD --name-only`
2. 从变更文件映射到受影响的页面/路由
3. 检测本地运行的开发服务器（3000/4000/8080 端口）
4. 只测受影响的页面
5. 交叉比对提交信息理解意图，验证变更是否实现了预期

如果无法从 diff 识别出页面，不跳过浏览器测试，改为 Quick 模式走一遍首页和主要导航。

---

## 回归测试模式

有历史 `baseline.json` 时可运行回归：

1. 执行完整测试
2. 加载历史基线
3. 对比：哪些问题已修复、哪些是新出现的、评分变化
4. 在报告末尾附加回归分析章节

---

## 注意事项

1. **每个问题必须有截图证据** -- 无例外
2. **先验证再记录** -- 重现一次确认非偶发
3. **绝不包含密码** -- 用 `[REDACTED]` 替代
4. **边发现边记录** -- 不批量写报告
5. **像用户一样测试** -- 用真实数据，走完整工作流
6. **深度优先于广度** -- 5-10 个有证据的问题 > 20 个模糊描述
7. **每次交互后检查控制台** -- 不浮出水面的 JS 错误也是 bug
8. **不拒绝使用浏览器** -- 用户触发 QA 就是要求浏览器测试，不用其他替代方案
