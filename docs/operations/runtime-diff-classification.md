# OpenClaw Runtime 差异分类

## 目标

在完成生产运行态备份与源码回收后，下一步不是直接合并代码，而是先把差异分类清楚：

- 哪些差异属于 OpenClaw 上游演进
- 哪些差异属于本地业务定制
- 哪些差异其实是运行态，不应进入源码仓库

本文用于指导第一轮差异分类，避免把生产快照直接当成长期源码真相，也避免把运行态配置误混入可升级代码层。

## 当前基线

当前应同时承认三份基线：

- 上游基线：`upstream/main`
- 本地维护基线：团队当前长期维护仓库
- 生产回收基线：从生产环境回收的源码快照与运行配置

分类时必须坚持以下原则：

- 生产回收基线是取证输入，不是未来长期真源码
- 本地维护基线是整理差异的主战场
- 上游基线用于判断哪些改动应该继续跟随 OpenClaw 主干

## 第一轮结论

### 1. 本地维护基线已经领先上游

本地维护仓库相对 `upstream/main` 已经存在一段独立提交历史，因此后续不能简单把所有生产差异都回灌到 core。应先判断这些差异是否与本地已存在改动重复、冲突或已经被替代。

### 2. 生产回收源码不是干净仓库

回收的生产源码目录不是标准 git 工作树，而是一个包含依赖、构建产物和配置的运行目录。它更接近“可运行快照”，不适合作为未来开发主仓库。

### 3. 差异同时存在于三层

第一轮结构比对已经说明，差异不是单点问题，而是同时分布在：

- core 代码目录
- Feishu 相关扩展
- skills 与脚本
- `server-config` 及运行配置模板

因此后续不能只做一次配置同步，必须做完整分层。

## 第一轮分类规则

### A 类：上游演进差异

特征：

- 文件路径、模块组织或平台代码形态已经明显不同
- 生产回收快照与本地维护基线看起来像不同时间点的 OpenClaw
- 差异广泛分布在核心目录，而不只出现在私有扩展中

处理方式：

- 不直接把生产快照覆盖本地维护基线
- 先以本地维护基线为主，再检查是否已经吸收或替代该能力
- 需要时回看 `upstream/main` 来判断是否仍有必要保留

### B 类：业务定制差异

特征：

- 明显与 Feishu、企业内部 workflow、私有 skills、业务脚本有关
- 不属于 OpenClaw 通用产品能力
- 更适合独立成 plugin、skill、script 或 overlay 配置

处理方式：

- 优先迁移到 overlay 层
- 避免继续散落在 core 或生产源码快照中
- 能做成 extension 就不要继续混入 core

### C 类：运行态差异

特征：

- 与 agent 绑定、workspace、sessions、memory、账号密钥有关
- 即使写在源码目录附近，也不属于源码资产

处理方式：

- 从源码仓库中剥离
- 收敛到 runtime 层
- 通过模板与部署变量渲染，而不是直接提交真实运行态文件

### D 类：噪音与非治理资产

特征：

- 临时打包产物
- 平台下载残留
- 本地系统生成的附带文件
- 仅用于一次性实验的副本

处理方式：

- 不参与主线合并
- 归档或清理

## 当前已确认的高优先级差异

### Feishu 扩展差异量很大

第一轮目录级比对表明，Feishu 扩展在生产回收快照与本地维护基线之间存在大量差异。这说明：

- Feishu 相关逻辑是当前最核心的定制承载区
- 这部分必须单独建清单，不适合混在整仓 diff 里处理
- 后续需要继续拆分成“通用扩展能力”和“业务环境定制”

治理建议：

- 先把账号路由、群策略、监控、文档、OSS、个性化 onboarding 分组
- 再判断每组是留在扩展本体，还是迁移到 overlay 配置与技能层

### `server-config` 已经承载了过多业务资产

第一轮比对表明，本地维护基线中的 `server-config` 不只是模板，还承载了：

- 私有扩展副本
- 私有 skills
- 业务脚本
- 环境相关配置

这会直接带来两个问题：

- 看起来像配置目录，实际却承担了代码仓库功能
- 升级主应用时无法区分“模板资产”和“运行态输入”

治理建议：

- `server-config` 只保留模板、示例与部署输入
- 私有扩展迁移到正式 extension 目录或独立 overlay 仓库
- 私有 skills 迁移到统一的 skills/overlay 结构

### 生产回收快照包含大量业务 skills

回收快照中的 skills 既包含上游已有技能，也包含明显业务化、环境化、流程化的技能集合。说明生产环境已经把“产品能力”和“业务能力”混放到同一层。

治理建议：

- 上游通用 skills 跟随 OpenClaw
- 业务专属 skills 收敛到 overlay
- 运行时挂载的技能目录应与源码目录解耦

### 存在非治理资产

例如压缩包、临时修改副本、平台附带文件等，不应进入长期治理主线。

治理建议：

- 在分类阶段就单独标记
- 不要让这些文件影响后续合并判断

## 下一步拆分顺序

### 1. 先锁定 Feishu 差异清单

把 Feishu 扩展相关差异拆成以下子类：

- 账号与 agent 路由
- 群策略与 mention 规则
- 回复派发与去重
- 文档、Drive、Bitable、Wiki、OSS 能力
- 监控与 webhook 安全
- onboarding 与个性化流程

### 2. 再锁定 `server-config` 边界

对 `server-config` 下每一项内容判断其归属：

- 配置模板
- 私有扩展源码
- 私有技能
- 一次性脚本
- 不应入库的真实运行态

### 3. 建立 overlay 目标结构

完成分类后，应为后续迁移准备目标落点：

- `extensions/*`：长期维护的私有扩展
- `skills/*` 或独立 overlay 仓库：长期维护的业务技能
- `deploy/` 或模板目录：部署渲染输入
- runtime：生产配置与数据

### 4. 最后再处理 core 差异

只有在业务定制与运行态都剥离完成后，才适合处理 core 差异。否则很容易把环境问题误判成产品问题。

## 验收标准

完成第一轮差异分类后，至少应满足：

- 每一类主要差异都有明确归属
- 生产回收快照不再被视为未来开发主仓库
- `server-config` 中哪些应保留、哪些应迁移、哪些应剥离已经清楚
- Feishu 相关改动已经能拆成可执行子任务
